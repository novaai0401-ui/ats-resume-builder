# Pocket Resume — Template Architecture Spec

> Companion to `REQUIREMENTS.md`. Pinned. Every Claude session reads
> it via `CLAUDE.md` before touching anything under
> `resume-builder-web/components/templates/`, the registry, or the
> normalization layer in `resume-builder-shared`.

This spec answers one question: **how do templates stay correct as the
product evolves?** Today there are 11 templates and 9 section keys.
Tomorrow there will be more sections (Publications, Volunteering,
Patents, Licenses for healthcare, References-on-request), more locales
(Hindi, Marathi, Tamil), more ATS variants (Workday-strict, LinkedIn-
import-friendly), and tailored variants generated by AI. The spec
makes that growth additive instead of a rewrite.

---

## §1. The template contract (what every template MUST do)

A template is a React component that renders a `Resume` into a
print-safe DOM tree. It does NOT own data shape, section order, or
section titles — those are global. It only owns visual presentation.

### 1.1 Inputs

Every template receives exactly one prop:

```ts
type TemplateComponentProps = {
  resumeData: ResumeImportResult;   // canonical resume shape, schema-validated
  locale?: SupportedLocale;          // ISO code, default 'en-IN'   (see §4)
  variant?: TemplateVariant;         // 'screen' | 'print' | 'ats-export'
};
```

A template must NOT take any other props. No layout knobs, no per-call
colour overrides. Templates that need toggles expose them through
declarative `TemplateCatalogItem` metadata (§2), never through props.

### 1.2 Outputs — three rendering variants

Every template renders into ONE React tree but reads `variant` to
decide what's safe to emit:

| Variant | Used by | Hard rules |
|---|---|---|
| `screen` | live preview, editor right pane | Free choice. Animations, colours, hover, web-only fonts. |
| `print` | "Print preview" button → `window.print()` | No animations. Page-break-after on each section header. Match Indian Letter / A4. Watermark in FREE plan. |
| `ats-export` | server PDF + DOCX generation | Single column, plain bullets, standard headings, no decorative imagery, no two-column flex containers, no CSS columns. **Even if a template's catalogue entry says `atsSafety: 'low'`, the `ats-export` variant must still emit ATS-survivable HTML** — otherwise the FREE flow breaks the contract on `/resume/template`. |

`variant` defaults to `screen`. A template that doesn't implement a
variant must fall back to `screen` and log a one-time warning to the
server-side logger via the templateUtils helper (don't crash).

### 1.3 Section contract

Templates render sections in the order given by
`getAtsSectionOrder(resume)`. They do not invent order, skip sections
the user has filled in, or rename headings. Specifically:

- The header section (`'header'`) is always rendered first and shows
  contact info per the resume's `contact` object.
- For each non-header key in `getAtsSectionOrder(resume)`:
  - The template asks `getAtsSectionTitle(section, locale)` for the
    rendered label.
  - It reads from a fixed accessor (§3.1) and skips silently if empty.
- Sections the user has explicitly hidden (`resume.hiddenSections`,
  see C-002 amendment below) are not rendered.
- Templates MUST render any unrecognised section key via a generic
  fallback that emits a `<section>` with the title from
  `getAtsSectionTitle` and bullets from the section payload. This is
  what makes new sections additive (§3).

### 1.4 Styling contract

- Use `@media print` for print-only styles.
- Use the design tokens exported from `templateUtils.tokens` for
  colour, type scale, spacing. Templates may extend but not replace
  the token names.
- All template-specific CSS lives inside the template's component
  file (CSS-in-JS via `style={{}}` or a CSS Module). No global
  selectors. No `!important`.
- Fonts: use only the four families already loaded in
  `app/layout.tsx` (`IBM Plex Sans`, `Literata`, `Source Sans 3`,
  `Work Sans`). Adding a font requires updating the preload link AND
  the CSP `font-src`. Don't do it for one template.

### 1.5 Accessibility contract

- Section titles use `<h2>` regardless of styling.
- Each experience / education / project / certification entry uses
  `<article>` or `<section>` with an `aria-labelledby` pointing at the
  entry's role/title.
- Bullet lists are `<ul>` with `<li>`, even if styled without bullets.
- No keyboard-trapping markup (no `tabindex > 0`, no inline forms).

## §2. Catalogue metadata (the registry, made declarative)

`TEMPLATE_CATALOG` in `resume-builder-shared/src/templates/catalog.ts`
is THE registry. Every template's static metadata lives there.
Templates that need behaviour toggles add fields to the catalogue
entry — never to the component prop list.

The current `TemplateCatalogItem` shape:

```ts
type TemplateCatalogItem = {
  id: TemplateCatalogId;
  name: string;
  description: string;
  tags: string[];
  atsSafety: 'high' | 'medium' | 'low';
  recommendedFor?: string[];
  industries?: string[];
  componentKey: TemplateCatalogId;
  isDefault?: boolean;
};
```

### 2.1 Required additions before R-030 ships

These fields are non-breaking (all optional) but every future template
must declare them. The five existing templates closest to the contract
should adopt these on the same commit that adds the field; the
remaining six get them in follow-ups before R-036.

```ts
type TemplateCatalogItem = {
  // ...existing fields above...

  /**
   * Canonical list of sections this template can render with first-class
   * styling. Sections NOT in this list still render via the generic
   * fallback (§1.3), but the template author has not optimised the layout
   * for them. The editor uses this to show a soft warning when the user
   * selects a template whose `supportedSections` doesn't cover their
   * filled sections.
   */
  supportedSections: AtsSectionKey[];

  /**
   * Locales the template renders correctly. A template that hard-codes
   * "Summary" in English declares only `['en-IN', 'en-US']`. A template
   * that wraps every label through `getAtsSectionTitle(section, locale)`
   * can declare every locale we support.
   */
  supportedLocales: SupportedLocale[];

  /**
   * Layout family. Drives:
   *   - the recommendation engine (don't recommend a two-column
   *     visual template for a Workday-only application);
   *   - the ATS-export variant — `multi-column` templates MUST still
   *     emit single-column HTML in the `ats-export` variant.
   */
  layout: 'single-column' | 'multi-column' | 'sidebar';

  /** True if this template renders cleanly inside an A4/Letter page break. */
  paginationSafe: boolean;

  /**
   * Variants this template implements. If 'ats-export' is missing, the
   * server falls back to ClassicATS for that user's export and warns
   * the user once.
   */
  implementedVariants: TemplateVariant[];
};
```

### 2.2 Catalogue tests (regression contract)

`tests/template-registry.test.ts` must assert:

- Every `TemplateCatalogItem.componentKey` resolves to a real component.
- `supportedSections` is a subset of `AtsSectionKey`.
- `supportedLocales` includes at least `'en-IN'`.
- `implementedVariants` includes at least `'screen'`.
- For every `atsSafety: 'high' | 'medium'`, `implementedVariants`
  includes `'ats-export'`.
- For every `paginationSafe: true`, a smoke test renders the template
  with a 3-page resume and asserts no orphaned headers (manual
  baseline; automate in days 0–30).

## §3. How a template adopts a new section without a rewrite

This is the future-proofing claim. Suppose tomorrow we add
`'volunteering'` to `AtsSectionKey`. The cost should be O(1), not
O(11).

### 3.1 Step-by-step (the only allowed path)

1. **Schema** — add `volunteering: VolunteeringItem[]` to
   `ParsedResumeSchema` in `resume-builder-schemas`. Rebuild `dist`.
2. **Section catalogue** — add `'volunteering'` to `AtsSectionKey`, to
   `ATS_SECTION_ORDER` at its canonical position (between Projects and
   Education, say), and to `SECTION_TITLE_MAP` with `{ 'en-IN':
   'Volunteering', 'hi-IN': 'स्वयंसेवा' }`. (See §4 — `SECTION_TITLE_MAP`
   gets locale support in R-040+.)
3. **Accessor** — add `getVolunteeringItems(resume)` to
   `templateUtils.tsx`. Mirror the shape of `projectItems` /
   `achievementItems`.
4. **Generic fallback** — every template ALREADY renders unknown
   sections via the fallback. So at this point, every existing
   template renders the volunteering section in plain
   "title + bullets" form. **No template files have been touched.**
5. **Opt-in upgrades** — templates that want first-class
   volunteering layout add the key to `supportedSections`, edit ONLY
   that file, and the generic fallback steps aside automatically.
6. **Parser** — extend `SECTION_SYNONYMS` so uploads recover
   "Volunteering", "Community work", "Voluntary experience", etc.
7. **Editor** — add a Volunteering section card behind a feature flag
   for one release while we backfill template support.

### 3.2 What this means in practice

- A new section is one schema change + one shared-constants change +
  one accessor + one parser change. The 11 templates and the export
  renderer keep working.
- A template that wants the new section to look beautiful upgrades on
  its own clock. Until it does, the user still sees the data, just in
  the fallback shape.
- This is exactly the contract that's been retroactively imposed on
  the existing `'achievements'` and `'languages'` sections — every
  template already renders both via accessors. The fix here makes
  that pattern the rule.

## §4. i18n contract (forward-loaded for R-040+)

The product is launching India-first in English. Hindi + regional
languages are explicitly planned for days 60+. The architecture must
not block that.

### 4.1 What templates do today (de facto)

- `getAtsSectionTitle` returns hard-coded English strings.
- Date formatting (`formatDateRange`) uses English month abbreviations.

### 4.2 What templates MUST do going forward

- `getAtsSectionTitle(section, locale)` — second parameter, defaulting
  to `'en-IN'`. The function reads from a per-locale map. Adding Hindi
  later is a data change, not a template change.
- `formatDateRange(start, end, locale)` — same pattern. Internally
  uses `Intl.DateTimeFormat` for everything except the case where the
  user typed a raw string we couldn't parse.
- Templates that hard-code labels ("Phone", "Email", "LinkedIn") MUST
  route them through `getContactLabel(field, locale)`.

### 4.3 What templates MUST NOT do

- Translate user content. The user's resume body stays in whatever
  language they typed it in. Labels translate; content doesn't.
- Use locale-detection libraries client-side. The locale flows in
  from `Settings → Language` (a future setting) or from the URL
  parameter on the embed preview, never from `navigator.language` —
  too brittle for resumes shared cross-device.

## §5. The export pipeline (server-side rendering)

Reference: `resume-builder-api/src/resume/resume.service.ts:601`
(generatePdf) + `renderResumeTemplateHtml` in the same package.

### 5.1 Contract

- The server renders the SAME React component the client uses, with
  `variant='ats-export'`. We do not have a separate HTML builder.
  (Historical fix: `4e39d25` / `414aa53` killed the parallel path
  because it diverged.)
- The export pipeline is responsible for: font embedding,
  page-break-after-on-section, watermark for FREE plan (gate per
  R-003), file naming via `buildExportFileName`.
- The PDF is rendered in headless Chrome (puppeteer). The DOCX is
  rendered from the same canonical resume via `renderResumeDocx` (text
  builder, NOT HTML — see `docx-export` package).

### 5.2 What this means for new templates

- Don't ship a template without the `ats-export` variant. The catalog
  test (§2.2) will fail.
- If a template uses CSS that doesn't render in puppeteer (e.g.
  `position: sticky`, custom scrollbars, ServiceWorker-cached fonts),
  the `ats-export` variant must fall back to print-safe CSS.
- Run the export tests in `tests/resume-export-pdf.e2e.test.cjs`
  whenever you touch a template.

### 5.3 DOCX renderer

- The DOCX path doesn't render HTML — it builds the document from the
  canonical resume by reading the same section accessors templates
  use. This means a new section gets DOCX support as soon as
  `templateUtils` has the accessor (§3.1 step 3). Visual templates
  don't affect DOCX output by design.

## §6. AI-generated tailored variants (forward-looking, R-034)

When the One-Click Tailor (R-034) lands, AI will produce a tailored
`ResumeVersion` that visually inherits the user's chosen base template
but may rewrite content per-bullet.

### 6.1 What stays the same

- Templates do NOT know whether they're rendering an AI-tailored
  version or a hand-edited one. Content is content.
- The diff view (R-034) operates above the template layer — it diffs
  the canonical resume JSON, not the rendered output.

### 6.2 What this means

- Templates must continue to render gracefully when bullets are
  longer than usual (AI tends to expand), when summaries get
  paragraph-style rewrites, and when achievement bullets carry
  metrics-heavy phrasing. Existing length-handling already covers
  this; future templates inherit the same constraint.

## §7. Recommendation engine

`src/lib/template-recommendation.ts` matches a user's industry +
experience level to a sorted list of templates. The signal it reads
is `TemplateCatalogItem.industries` + `recommendedFor`. New templates
add to those arrays; the engine doesn't need updating.

A template with `atsSafety: 'low'` is allowed in the catalogue but
the recommendation engine must NEVER surface it as the top
recommendation. The user has to actively pick it from the gallery,
and the picker shows a clear "ATS risk" badge (already in place).

## §8. Removing or replacing a template

- Removing a template is a destructive change because users have
  `Resume.templateId` references in the DB. Replacement path:
  1. Add the new template under a new `id`.
  2. Update `resolveTemplateCatalogId` so the old `id` returns the
     new one as a redirect.
  3. Run a backfill that updates any `Resume.templateId` from the old
     id to the new one. Keep the redirect alive for at least 90 days.
  4. After 90 days + zero DB references, remove the old template
     file. The catalogue test must pass with the entry gone.
- Templates cannot be deleted in the same commit that adds the
  replacement. Always two commits.

---

## §9. The non-negotiables (for fast reference)

These are the rules you should be able to recite from memory before
touching any template code:

1. One prop (`TemplateComponentProps`), three variants.
2. Read section order from `getAtsSectionOrder`; never invent it.
3. Read section titles from `getAtsSectionTitle`; never hard-code.
4. Unknown sections render via the generic fallback; don't crash.
5. ATS-export variant is single-column, plain, no decorative imagery.
6. Design tokens live in `templateUtils.tokens`; templates extend, never replace.
7. New sections, new locales, new variants are additive — no rewrite path.
8. Removing a template takes two commits and a 90-day redirect.
9. Outcome attribution (C-007) is preserved through any AI-tailored variant.
